SSH client · roaming terminal · Android & Linux

A remote terminal that refuses to guess.

Pylon connects to the servers you already have, over the SSH they already run, but it never takes a host on faith, never holds your private key, and never lets a server's output reach further than the screen it was drawn on.

Build it Read the specification

Most SSH attacks don't break the cryptography. They wait for you to type yes.

SSH's mathematics have held up for decades. What fails is everything around them: a first-connection prompt people approve without reading, private keys copied onto every laptop and phone, agents forwarded to servers that can then sign as you elsewhere, legacy algorithms left enabled "for compatibility", and a terminal that will faithfully interpret any byte a compromised server sends.

Each of these is fixable from the client side, without changing a single server. Pylon is that client. It speaks ordinary SSH to the world, but a deliberately narrow, strictly enforced SSH, and it moves the decisions that people get wrong under pressure out of the moment of connection.

  • Trust on first use"The authenticity of host … can't be established. Continue? (yes/no)"
  • Keys on disk~/.ssh/id_ed25519 on every device, backed up who-knows-where
  • Forwarded agentsa compromised bastion signs logins to your other servers
  • Downgrade & Terrapinold ciphers and kex methods kept for the one router that needs them
  • Hostile outputescape sequences that rewrite your clipboard or fake a prompt
  • Fragile sessionsa train tunnel, a Wi-Fi hop, a closed laptop lid: the shell is gone

Host trust

A host key earns trust before a single byte of your session leaves the device.

Pylon has no "accept and continue" button. A host's key is checked during the key exchange, and if none of the sources below vouches for it, the connection ends before authentication, so a man in the middle learns nothing: not your user name, not a signature, not a keystroke.

QR codes, not squinting

The server's console prints a one-line payload, pylon-hostkey/1 HOST[:PORT] SHA256:…, as a QR code. Pylon scans it and pins only if the key presented in a fresh exchange matches, and only for that host and port.

Its own DNSSEC validator

OpenSSH's VerifyHostKeyDNS believes the resolver's "authenticated" bit. Pylon validates every signature itself from the IANA root anchors, so a hostile Wi-Fi resolver can't vouch for anything. Insecure, bogus or indeterminate answers are shown, never trusted.

A changed key is a hard stop

The screen names the old pin and when it was made. The only ways forward are to disconnect or to re-verify from scratch; every re-pin is kept in pylon history. A certificate from a CA you trust doesn't override a pin either.

On the wire

One connection, from connect() to a shell.

Pylon offers a short list of modern algorithms and nothing else; the rest are not switched off, they are absent from the code. The post-quantum hybrid comes first, strict key exchange (the Terrapin fix) is required, and every user signature names both this server's key and this exact session.

Key custody

Pylon has nothing to steal.

There is no private key in Pylon. Every signature comes from Symbolon, a separate agent that holds threshold keys (no single device has the whole key) and shows a consent sheet naming the user, the host and the key before it signs.

Before it asks for a signature, Pylon hands the agent the host key, the session hash H and the host's own signature over H. The agent checks that signature itself and refuses anything for a different session. A compromised server therefore cannot relay your login to another server, the classic risk of agent forwarding, which Pylon doesn't offer at all. To reach a host behind a bastion, Pylon tunnels through it (-J) and verifies each hop under its own pin.

Without Symbolon, Pylon also works with a FIDO2 security key, an Android Keystore key, an external agent or an imported key file, each behind an explicit warning of exactly what that gives up.

The Pylon protocol experimental

Log in with SSH. Stay connected without it.

Once logged in, Pylon can push a small, signed pylond to the server over the same SSH connection (no root, nothing installed beforehand) and move the session onto its own UDP protocol. The session's keys are exchanged inside the already-verified SSH channel, so only the host you verified, reached after your authentication, can complete it; then it adds what TCP can't give.

Post-quantum, forward-secret

X25519 + ML-KEM-768, new keys every two minutes, so traffic recorded today stays sealed even against a future quantum computer.

Silent to scanners

An unauthenticated datagram gets one constant-time MAC check and no reply. Under load, a cookie is required before any asymmetric work.

Re-attach needs you

A stolen, unlocked phone can't resume your shell: re-attaching from another device or after the app closed goes through a fresh SSH login, which needs a new signature from your key's custodian.

The v1 handshake is not yet a verified Noise pattern, and its keys are not yet cryptographically bound to the SSH exchange hash (the specification's target). It is off unless you pass --pylond, and the specification requires a formal model and an external review before it becomes the default.

Code pushed to your servers

Nothing runs on a host unless a quorum signed it and the world can see it.

Pushing a binary to a server is exactly what an attacker who stole a maintainer's key would want to do. So pylond is pushed only if every check below passes, offline, before a byte reaches the host.

  1. Reproducible buildx86-64 and AArch64, code images that match between honest builders
  2. k of n signaturesseparate Ed25519 release keys, one per maintainer device
  3. Transparency logan RFC 9162 Merkle tree; inclusion and consistency proofs under a head signed by log keys the maintainers don't hold
  4. No rollbacka release counter that only goes up
  5. Hash checked on the hostcontent-addressed, mode 0500 in a 0700 cache, run as you, never root

Three release keys are pinned, any two of which must sign. No signed release is bundled yet, so for now only developer options (announced as such on every use) push a pylond.

The terminal

Output from a server is treated as an attack until proven otherwise.

The terminal emulator is the largest parser of attacker-controlled bytes in any SSH client. Pylon's runs in its own confined process, away from the keys and connections (on the desktop, one sandbox per terminal; on Android today, one isolated process shared by all terminals), written in Resid: total parsers, checked arithmetic, and secrets typed as Secret so they can't be logged or compared in variable time.

  • Clipboard writes need a per-host grant; clipboard reads don't exist.
  • No read-back: title reports and setting queries that echo attacker text as input are not implemented.
  • Pastes with newlines or control characters are shown before they're sent, and pasted text can't end a bracketed paste early.
  • Links show their real target before opening.
  • Pylon's own prompts are drawn outside the terminal, so output can't imitate them.
  • Keystroke timing is hidden in fixed 20 ms frames with chaff.

Pylon and ssh

Same servers, same protocol. Different defaults, and a different idea of who decides.

Pylon is not a replacement for the SSH protocol or for sshd: every server keeps running OpenSSH. It replaces the client (the ssh command, Termius, ConnectBot, JuiceSSH). Much of what Pylon enforces exists in modern OpenSSH as options; the difference is that in Pylon they are not options.

When to keep using ssh: scripts and automation that need its full configuration surface, servers that only speak algorithms Pylon dropped, X11 forwarding, and anywhere you need the most battle-tested implementation rather than the strictest one.

Where it stands

Honest about what's done.

Working

  • Strict SSH client with the post-quantum hybrid
  • Pins, QR, host certificates, SSHFP + DNSSEC
  • Session-bound agent signing
  • Shells, exec, -L -D -R, -J, SFTP browser
  • Android app and Linux desktop with tabs and splits
  • 153 interop and hostile-server cases, fuzzing

Experimental

  • The Pylon UDP protocol and pylond
  • Persistent sessions and re-attach
  • The isolated local shell (Android not yet verified on a device)

Not yet

  • The first signed, logged pylond release
  • Formal model and external review of the protocol
  • Live DNSSEC against the real root in CI
  • Windows, macOS, iOS

Try it

Build, pin, connect.

# needs the Resid toolchain (residc)
residc cli/pylon.resid -o build/pylon

# on the server's console, read its key fingerprint
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

# on your machine, pin it, then connect through any session-bind capable agent
build/pylon pin example.org SHA256:...
eval "$(symbolon ssh-agent ~/.symbolon &)"
build/pylon alice@example.org

Android builds come from the apk workflow and are attached to each release. The full design, threat model and hardening review are in SPEC.md.
